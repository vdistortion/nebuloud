# Nebuloud — архитектура и план

> Единый рабочий документ проекта. Если старые заметки, разговоры с ИИ или код расходятся с этим файлом, актуальным считается этот файл, пока решение не изменено здесь.

**Статус:** production работает на Directus; каталог и сайты артистов собираются
отдельно в SSG, домены артистов читаются из Directus.

**Дата фиксации:** 2026-09-24

**Текущее техническое состояние:** Directus является источником контента и доменов артистов; каталожная сборка и отдельные сайты артистов генерируются как статические сайты.

## 1. Что строим

Nebuloud — музыкальный сайт и будущий движок готовых сайтов для музыкантов.

Долгосрочная цель:

- один сайт для одного артиста;
- один каталог с несколькими артистами;
- в будущем — готовый настраиваемый сайт для стороннего музыканта;
- в ещё более далёком будущем — несколько сайтов на общей платформе.

Ближайшая цель не является «сразу сделать движок». Ближайшая цель — сделать один убедительный, работающий сайт музыкального каталога на реальных данных из старой версии.

Главный принцип:

> Сначала один хороший продуктовый сценарий и рабочий контент. Обобщение архитектуры — только после появления второго реального сценария.

Проект имеет смысл даже если им никогда не воспользуется никто, кроме автора.

## 3. Жёсткая критика прежнего плана

### 3.1. Начинать с движка было ошибкой

Проект пытался одновременно решить задачи:

- универсальный сайт для любых музыкантов;
- multi-tenant;
- поддомены;
- темы и смена структуры страниц через JSON;
- Angular;
- Nx;
- pnpm;
- SSR/SSG;
- собственный TypeScript API;
- PostgreSQL;
- Docker;
- админка;
- миграция существующего каталога.

Это не план первого продукта, а план небольшой платформы. Для одного разработчика такая постановка почти гарантирует месяцы инфраструктурной работы без законченного сайта.

### 3.2. Nx и pnpm были сложностью без текущей пользы

В проекте сейчас одно Angular-приложение. Монорепозиторий и несколько приложений не дают заметного выигрыша, зато увеличивают количество конфигурации и ошибок. Текущий обычный Angular workspace на npm — правильная база.

Если через некоторое время появятся реально независимые приложения, вернуться к Nx можно будет без потери продуктовых данных.

### 3.3. Собственный backend не нужен

Писать API, авторизацию, админку и базу данных самостоятельно нерационально. Directus уже закрывает значительную часть этой задачи и лучше соответствует текущим навыкам и цели проекта.

Но Directus тоже не должен быть первым препятствием. До подключения CMS каталог должен нормально отображаться из локальной модели данных.

### 3.4. «Система тем» преждевременна

Нужно заранее не закрывать путь к темизации, но сейчас не надо строить JSON, который меняет структуру всего сайта. Сначала делаем один layout и выносим визуальные решения в SCSS-токены и понятные компоненты.

Будущая темизация должна начинаться с:

- цветов;
- шрифтов;
- отступов;
- радиусов;
- вариантов карточек;
- нескольких layout-вариантов.

Она не должна появляться до появления второго реального дизайна или второго клиента.

### 3.5. Не нужно переписывать каталог ради переписывания

В старую базу вложено много времени. Её задача сейчас — стать источником реальных данных для нового интерфейса. Сначала отделяем данные от компонентов и сохраняем семантику, затем при необходимости меняем формат.

## 4. Принятые решения

### Стек сейчас

- Angular 22;
- обычный Angular CLI workspace;
- npm;
- TypeScript;
- SCSS;
- Directus + PostgreSQL как единственный источник контента;
- Angular SSG/prerender по возможности сразу;
- без Nx;
- без собственного backend;
- Directus + PostgreSQL для production-контента;
- Docker Compose для production;
- без отдельной админки на первом этапе;
- тесты не являются блокером первого визуального результата.

### Контент сейчас

Сохраняем весь существующий каталог:

- всех артистов;
- альбомы;
- песни;
- тексты;
- песни вне альбомов;
- ссылки на стриминги;
- видео;
- изображения и галереи.

На первом этапе данные остаются локальными. Компоненты не должны зависеть от того, были данные загружены из TypeScript, JSON или Directus.

### Directus сейчас

Directus + PostgreSQL рассматриваются как следующий источник контента, по аналогии с `kira-sekira`.

Правильная граница:

```text
страницы и UI
       ↓
ContentService / модели frontend
       ↓
Directus production
```

При подключении Directus меняется адаптер получения и нормализации данных, а не все страницы приложения.

### Много артистов

Каталог остаётся отдельным приложением. У артиста можно указать полный hostname в `artists.site_domain`. Сборка создаёт отдельный SSG-артефакт для каждого артиста с доменом; пустое поле оставляет его страницы в каталоге по `/artist/<slug>/...`.

То есть сейчас:

```text
artist-domain.example/
artist-domain.example/album/<slug>
nebuloud.zvalentin.com/artist/geval
```

Поле `site_domain` в Directus — единственный редактируемый источник доменов.
Скрипт сборки использует эти данные для SSG-артефактов, ссылок, nginx host map,
Caddy host list и CORS allowlist. Конфиги для сборки и деплоя являются
производными файлами, их вручную не редактируют. Изменение домена требует
повторной сборки и деплоя.

Артист или владелец сайта меняет данные в Directus. Angular-приложение использует тот же UI и тот же контракт контента, но получает данные не из локальных файлов.

## 6. Маршруты первой версии

Сохраняем понятную текущую структуру URL, не изобретаем новую ради самого изменения:

```text
/                                      каталог артистов
/artist/:artist                       профиль артиста
/artist/:artist/albums                 дискография артиста
/artist/:artist/album/:album           альбом и треклист
/artist/:artist/songs                  песни с текстами
/artist/:artist/songs?other=true          фильтр песен вне альбомов
/artist/:artist/song/:song             текст и информация о песне
/artist/:artist/video                  видео артиста
/artist/:artist/images                 список галерей/фотографий
/artist/:artist/images/:gallery        галерея
```

Почему не использовать сразу `/album/:slug` без артиста: на первом этапе каталог — один общий сайт с несколькими артистами. Артист в URL явно предотвращает конфликты одинаковых названий.

На отдельном сайте артиста используется корень `/` и чистые пути `/album/:album`, `/song/:song`, `/songs`, `/video` и `/images`. Внутренние ссылки остаются общими компонентами, но URL выбираются по режиму приложения.

## 7. Данные и модель контента

### Модель Directus

Минимальные коллекции:

- `artists`;
- `albums`;
- `songs`;
- `videos`;
- `galleries`;
- `gallery_images`;
- возможно `streaming_links` или JSON-поле ссылок.

Связи:

- артист имеет альбомы, песни, видео и галереи;
- альбом содержит песни;
- песня может не принадлежать альбому;
- песня имеет текст;
- у сущностей есть стабильный slug/ID;
- URL не строятся по отображаемому названию напрямую.

Одинаковые названия альбомов и песен допустимы. Уникальность должна быть как минимум в пределах артиста и типа сущности.

## 8. Архитектура frontend

Структура Angular workspace:

```text
projects/
  catalog/                 приложение каталога и /artist/:slug для артистов без домена
  artist/                  приложение одного сайта артиста, SSG-сборка на каждый домен
  shared/                  страницы, UI, модели, адаптер Directus и сервисы
```

Оба приложения используют общий код через alias `@shared`. У них отдельные
маршруты и SSG-конфигурации, а доменное соответствие остаётся в Directus.

Источник данных приложения — `DirectusContentSource`, доступный страницам через
`ContentService`.

Страницы не импортируют файлы конкретного артиста напрямую и не знают о формате ответа Directus.

### Контракт Directus

Страницы используют нормализованные frontend-модели, а `DirectusContentSource`
преобразует ответы API в этот контракт.

Минимальная схема:

```text
artists
  ├─ albums
  │    └─ songs
  ├─ songs
  ├─ videos
  └─ galleries
         └─ gallery_images
```

Коллекции и ключевые поля:

- `artists`: `slug`, `name`, `image`, `country`, `description`, `site_domain`;
- `albums`: `artist`, `slug`, `title`, `year`, `cover`, `description`, `sort`;
- `songs`: `artist`, `slug`, `title`, `aliases`, `lyrics`, `authors`, `video_url`, `sort`;
- `album_songs`: `album`, `song`, `sort` — если одна песня может входить в несколько альбомов;
- `galleries`: `artist`, `slug`, `title`, `sort`;
- `gallery_images`: `gallery`, `image`, `sort`;
- `streaming_links`: `artist` или `album`, `service`, `url`, `sort`.

Правила:

- отображаемое название не является идентификатором;
- `slug` уникален в пределах артиста и типа сущности;
- песня может существовать без альбома;
- одна песня может быть связана с несколькими альбомами;
- порядок треков и фотографий хранится явно;
- Directus-ответы преобразуются в `ArtistProfile`, `CatalogAlbum` и `CatalogSong` внутри data layer;
- страницы не получают Directus SDK напрямую.

### Что переносим из `kira-sekira`

- разделение `pages / features / layout / ui`;
- Signals для состояния;
- отдельный сервис контента;
- отдельный SEO-сервис;
- SCSS design tokens;
- prerender маршрутов из списка локальных slug-ов;
- принцип: данные отдельно, представление отдельно.

### Что не переносим сейчас

- Directus snapshot и сиды;
- Docker Compose;
- Garage, backup и sync-инфраструктуру;
- отдельные приложения `main` и `models`;
- конфигурацию сайтов, продублированную в нескольких приложениях;
- собственную API-типизацию и M2M-формат Directus;
- админку.

## 9. Дизайн как первый этап

Начинаем не с базы данных и не с инфраструктуры, а с переноса визуального языка `new_design` в Angular.

### Визуальное направление

- тёмный фон;
- красно-оранжевый основной акцент;
- фиолетовые фоновые подсветки;
- полупрозрачные панели;
- тонкие границы;
- карточки с hover-состояниями;
- крупные заголовки;
- адаптивная сетка;
- навигация и breadcrumbs;
- карточки альбомов, артистов, видео и фотографий.

### Важная оговорка

`new_design` сейчас показывает много экранов, но не является единым production-дизайн-системой. Есть повторяющиеся CSS-блоки, разные варианты header/hero и демонстрационные элементы вроде эмодзи вместо изображений.

Поэтому переносим:

- композицию экранов;
- цветовое и типографическое направление;
- сетки и состояния компонентов;
- responsive-поведение.

Не переносим механически:

- inline-CSS;
- повторяющийся код из каждого HTML;
- демонстрационные emoji-placeholder;
- сомнительные анимации на каждом элементе;
- `admn.html` как обещание полноценной админки.

### Порядок визуальной реализации

1. Общие токены и базовая типографика.
2. Общий header и навигация.
3. Страница каталога артистов (`index.html`).
4. Профиль артиста (`profile.html`).
5. Карточка/список альбомов (`albums.html`).
6. Страница альбома и треклист (`album.html`).
7. Страница песни и текста (`text.html`).
8. Видео и фотографии (`video.html`, `foto.html`).
9. Адаптивная версия и состояния пустых/неполных данных.

Первый законченный срез — профиль одного артиста на реальных данных, включая переход в один альбом и одну песню. После этого расширяем на весь каталог.

## 11. Что сознательно отложено

### Публичное API, движок и SaaS — решение после production

После публикации первого рабочего сайта отдельно оценить, нужен ли публичный API и превращать ли Nebuloud в настоящий движок.

Не делать API только потому, что «так положено для движка». Сначала нужны реальные сценарии:

- второй независимый сайт;
- внешний пользователь или артист;
- повторяющийся процесс наполнения контента;
- понятная польза от API, а не только технический интерес.

Возможные будущие направления:

- публичное API для каталогов и сайтов артистов;
- SaaS для создания сайтов музыкантов;
- платные темы или layout-варианты;
- платный хостинг и управление контентом;
- расширенные функции: домен, аналитика, импорт каталога, модерация;
- мобильное приложение — только если веб-версии будет недостаточно;
- Telegram-бот для поиска, предложений исправлений, уведомлений или работы с каталогом;
- интеграции с Telegram без дублирования всей логики сайта.

### ИИ — отдельное направление для оценки

После появления рабочего контентного процесса подумать, где ИИ действительно полезен:

- предварительная проверка предложенных исправлений текстов;
- поиск дубликатов и похожих песен;
- помощь в нормализации названий, авторов и метаданных;
- поиск по смыслу и рекомендации;
- подготовка описаний, тегов и кратких справок;
- интерфейс помощника через сайт или Telegram.

ИИ не должен автоматически публиковать тексты или менять каталог без модерации. Сначала нужно понять реальные задачи, стоимость и риски ошибок.

Пока это идеи, а не обязательства. Сначала нужен один хороший продукт, затем проверка спроса и только потом — приложения, боты, ИИ-интеграции, публичные контракты, тарифы и биллинг.

### Пользовательские предложения по текстам песен — важно после production

После публикации сайта обязательно добавить механизм обратной связи для контента:

- предложить исправление существующего текста песни;
- отправить текст песни, которого ещё нет в каталоге;
- указать источник или комментарий к предложению;
- не публиковать предложение автоматически без проверки.

Варианты реализации пока не выбраны:

- форма на сайте → запись в отдельную коллекцию Directus;
- форма на сайте → email;
- форма → бот/модерационный канал;
- комбинация Directus + уведомление.

Рабочий контент должен изменяться только после модерации. Это важная production-функция, но её не нужно реализовывать до публикации основного каталога.

Предпочтительный сценарий:

```text
страница песни → форма предложения → content_suggestions в Directus
                → уведомление владельцу → ручная модерация → изменение songs
```

Форма должна поддерживать исправление существующего текста и отправку нового
текста без регистрации. В запись сохраняются песня/артист, текущий и новый
текст, комментарий, источник и необязательный контакт автора. Позже добавить
защиту от спама: honeypot, rate limit и при необходимости Turnstile.

### Недостающие музыкальные сущности

По итогам анализа старого сайта «Мастера» в будущем могут понадобиться:

- **История артиста** — хронология событий по годам: создание группы, составы, релизы, концерты и важные события.
- **Участники** — музыканты, роли, периоды участия, текущий/бывший состав.
- **Тип релиза** — студийный альбом, концертный альбом, сборник, трибьют, совместная работа, DVD, сингл или EP.
- **Публикации** — интервью, рецензии и статьи с изданием, годом и внешней ссылкой.
- **Новости** — текущие события, новые релизы и объявления.
- **Социальные и официальные ссылки** — VK, YouTube, сайт и контакты отдельно от стриминговых сервисов.
- **События/концерты** — только если появится актуальная потребность в расписании или архиве выступлений.
- **Документы/книги** — PDF, книги, буклеты и архивные материалы с автором, описанием, годом, обложкой, источником и правовым статусом.
- **Публикация контента** — статус `published/draft/hidden` для возможности временно скрывать артиста, релиз, песню, галерею или файл без удаления.
- **Единый стандарт slug** — отдельная задача: выбрать одну транслитерацию для новых артистов, альбомов, песен, галерей и документов; существующие slug не менять автоматически без таблицы переноса.

Для подготовки стандарта создана утилита `scripts/slugify.py`. На следующем
этапе её правила нужно использовать в Directus hook/Flow: генерировать slug
только при создании записи или пока поле пустое, а ручное исправление больше не
перезаписывать.

Будущий генератор slug для админки Directus должен учитывать языки названий:

- русский — ГОСТ Р 7.0.34-2014;
- украинский — ДСТУ 9112:2021, система Б;
- немецкий — отдельного обязательного стандарта для URL пока не выбираем; использовать практическое правило `ä→ae`, `ö→oe`, `ü→ue`, `ß→ss`.

В Directus нужно показывать автоматически сгенерированный slug до сохранения и
разрешать ручное редактирование. Автогенерация должна происходить только при
пустом slug, чтобы изменение названия не ломало уже опубликованный URL.

Для текущего мигрированного каталога допустим отдельный автоматический проход с
последующей ручной проверкой исключений. Перед заменой обязательно сохранить
таблицу `старый slug → новый slug`, проверить коллизии в пределах артиста и
обновить SSG-маршруты.

### Книга «Мастер. 100 страниц»

Исходный материал находится отдельно:

```text
/home/v/Projects/master-metal-history/book.pdf
```

После проверки разрешения на публикацию добавить книгу в Nebuloud как отдельный
архивный материал артиста «Мастер», а не как обычную фотогалерею или статью.
Предпочтительный маршрут:

```text
/artist/master/library/master-100-pages
```

Минимальная будущая сущность `documents`:

- `artist`;
- `slug`;
- `title`;
- `author`;
- `year`;
- `description`;
- `file` — PDF в Directus Files;
- `cover` — необязательная обложка;
- `source_url`;
- `rights_note`;
- `sort`.

На первом этапе достаточно страницы с описанием, обложкой, кнопками «Читать в
браузере» и «Скачать PDF». Не добавлять PDF в Git и не встраивать тяжёлый
сторонний PDF-viewer без необходимости: браузер умеет открывать PDF напрямую.

Пока это только список для планирования. Не добавлять сущности в Directus и интерфейс до отдельного этапа.

- Fastify/NestJS и собственный API;
- ручная работа с PostgreSQL;
- авторизация;
- полноценная админка;
- JSON-конфигурация, меняющая структуру сайта;
- Nx;
- Redis и сложное кеширование;
- загрузка и конвертация видео;
- платформа для массового создания сайтов;
- автоматическая миграция всего контента в Directus до проверки модели.

Это не отменённые идеи, а идеи без права мешать первому рабочему сайту.

## 12. Критерии готовности первого результата

Первый результат считается полезным, если:

- `npm start` запускает сайт без ручных обходов;
- каталог артистов открывается;
- профиль артиста открывается по прямой ссылке;
- из профиля можно перейти в альбом;
- из альбома можно перейти в песню;
- текст песни отображается корректно;
- страницы используют реальный каталог, а не mock-данные;
- дизайн соответствует направлению `new_design`;
- сайт работает на мобильной ширине;
- production build проходит;
- prerender не ломается на существующих маршрутах;
- добавление нового артиста в Directus не требует копирования Angular-компонентов;
- production можно собрать из чистого checkout; prerender получает маршруты из Directus.

## 13. Журнал решений

Даты здесь не фиксируем: важна актуальная договорённость, а не история изменений.

- Удалён Nx-эксперимент `feat/nx-refactor`; работа продолжается в обычном Angular `main`.
- Angular обновлён до 22.
- `pfan-stack-main_combined.txt` признан неактуальным boilerplate и не используется как основа.
- Весь существующий музыкальный каталог сохраняется.
- Directus + PostgreSQL стали единственным источником контента.
- Сначала реализуется один дизайн и рабочий вертикальный срез; темизация отложена.
- `ContentService` — единая граница между страницами и Directus.
- Для Nebuloud создан отдельный Docker-стек `Directus + PostgreSQL`; `kira-sekira` для этого не используется.
- Временный production-адрес Directus выбран как `api.nebuloud.zvalentin.com`; локально продолжает использоваться `http://localhost:8056`.
- Базовые коллекции и relations созданы в Directus; аватары, обложки и фотогалереи хранятся в Directus Files.
- Production подключается к общей инфраструктуре через внешние сети `caddy` и `garage` из отдельного репозитория `vps-infra`; деплой web автоматизируется GitHub Actions.
- Caddy используется как внешний reverse proxy и TLS-терминатор, nginx внутри `web` — как сервер готовой Angular-статики.
- `DirectusContentSource` обслуживает главную страницу, профиль артиста, альбом, песню, списки песен, видео и галереи.
- Production Flow предложений по текстам настроен вручную в Directus: webhook создаёт `content_suggestions` и отправляет уведомление в Telegram; конфигурацию Flow ещё нужно сделать воспроизводимой через bootstrap.
- Angular-компоненты переименованы в короткий стиль без суффикса `.component`: `artist-page.ts`, `ArtistPage` и т.д.
- `ARCHITECTURE.md` — единый источник текущих архитектурных решений.
