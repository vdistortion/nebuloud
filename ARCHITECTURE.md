**Дата фиксации:** 2026-09-18

**Текущее техническое состояние:** приложение собирает 824 prerender-маршрута, но production-сборка завершается ошибкой из-за initial bundle размером около 2.72 MB при лимите 1 MB. ## 1. Что строим

Nebuloud — музыкальный сайт и будущий движок готовых сайтов для музыкантов.

Долгосрочная цель:

- один сайт для одного артиста;
- один каталог с несколькими артистами;
- в будущем — готовый настраиваемый сайт для стороннего музыканта;
- в ещё более далёком будущем — несколько сайтов на общей платформе.

Ближайшая цель не является «сразу сделать движок». Ближайшая цель — сделать один убедительный, работающий сайт музыкального каталога на реальных данных из старой версии.

Главный принцип:

> Сначала один хороший продуктовый сценарий и рабочий контент. Обобщение архитектуры — только после появления второго реального сценария.

Проект имеет смысл даже если им никогда не воспользуется никто, кроме автора.

## 3. Жёсткая критика прежнего плана

### 3.1. Начинать с движка было ошибкой

Проект пытался одновременно решить задачи:

- универсальный сайт для любых музыкантов;
- multi-tenant;
- поддомены;
- темы и смена структуры страниц через JSON;
- Angular;
- Nx;
- pnpm;
- SSR/SSG;
- собственный TypeScript API;
- PostgreSQL;
- Docker;
- админка;
- миграция существующего каталога.

Это не план первого продукта, а план небольшой платформы. Для одного разработчика такая постановка почти гарантирует месяцы инфраструктурной работы без законченного сайта.

### 3.2. Nx и pnpm были сложностью без текущей пользы

В проекте сейчас одно Angular-приложение. Монорепозиторий и несколько приложений не дают заметного выигрыша, зато увеличивают количество конфигурации и ошибок. Текущий обычный Angular workspace на npm — правильная база.

Если через некоторое время появятся реально независимые приложения, вернуться к Nx можно будет без потери продуктовых данных.

### 3.3. Собственный backend не нужен

Писать API, авторизацию, админку и базу данных самостоятельно нерационально. Directus уже закрывает значительную часть этой задачи и лучше соответствует текущим навыкам и цели проекта.

Но Directus тоже не должен быть первым препятствием. До подключения CMS каталог должен нормально отображаться из локальной модели данных.

### 3.4. «Система тем» преждевременна

Нужно заранее не закрывать путь к темизации, но сейчас не надо строить JSON, который меняет структуру всего сайта. Сначала делаем один layout и выносим визуальные решения в SCSS-токены и понятные компоненты.

Будущая темизация должна начинаться с:

- цветов;
- шрифтов;
- отступов;
- радиусов;
- вариантов карточек;
- нескольких layout-вариантов.

Она не должна появляться до появления второго реального дизайна или второго клиента.

### 3.5. Не нужно переписывать каталог ради переписывания

В старую базу вложено много времени. Её задача сейчас — стать источником реальных данных для нового интерфейса. Сначала отделяем данные от компонентов и сохраняем семантику, затем при необходимости меняем формат.

## 4. Принятые решения

### Стек сейчас

- Angular 22;
- обычный Angular CLI workspace;
- npm;
- TypeScript;
- SCSS;
- статические TypeScript-данные на первом этапе;
- Angular SSG/prerender по возможности сразу;
- без Nx;
- без собственного backend;
- без PostgreSQL до подключения Directus;
- без Docker для frontend-этапа;
- без отдельной админки на первом этапе;
- тесты не являются блокером первого визуального результата.

### Контент сейчас

Сохраняем весь существующий каталог:

- всех артистов;
- альбомы;
- песни;
- тексты;
- песни вне альбомов;
- ссылки на стриминги;
- видео;
- изображения и галереи.

На первом этапе данные остаются локальными. Компоненты не должны зависеть от того, были данные загружены из TypeScript, JSON или Directus.

### Directus позже

Directus + PostgreSQL рассматриваются как следующий источник контента, по аналогии с `kira-sekira`.

Правильная граница:

```text
страницы и UI
       ↓
ContentService / модели frontend
       ↓
локальные данные сейчас | Directus позже
```

При подключении Directus меняется адаптер получения и нормализации данных, а не все страницы приложения.

### Много артистов

Много артистов поддерживаем сразу на уровне данных и маршрутов, потому что это уже есть в старом каталоге. Но multi-tenant в смысле отдельных сайтов, поддоменов и независимых тем откладываем.

То есть сейчас:

```text
nebuloud.ru/artist/master
nebuloud.ru/artist/geval
```

Позже возможно:

```text
master.nebuloud.ru
geval.nebuloud.ru
```

Переход на поддомены не должен требовать переписывания контентной модели.

## 5. Целевые пользовательские сценарии

### Хаб

Посетитель открывает Nebuloud и:

1. видит список артистов;
2. ищет артиста;
3. открывает профиль артиста;
4. переходит в его дискографию, песни, видео или фотографии.

### Сайт артиста

Посетитель:

1. открывает профиль артиста;
2. видит краткую информацию и ссылки;
3. открывает альбом;
4. выбирает песню;
5. читает текст;
6. переходит к клипу, стримингу или галерее.

### Будущий клиентский сайт

Артист или владелец сайта меняет данные в Directus. Angular-приложение использует тот же UI и тот же контракт контента, но получает данные не из локальных файлов.

## 6. Маршруты первой версии

Сохраняем понятную текущую структуру URL, не изобретаем новую ради самого изменения:

```text
/                                      каталог артистов
/artist/:artist                       профиль артиста
/artist/:artist/albums                 дискография артиста
/artist/:artist/album/:album           альбом и треклист
/artist/:artist/songs                  песни с текстами
/artist/:artist/songs/other            песни вне альбомов
/artist/:artist/song/:song             текст и информация о песне
/artist/:artist/video                  видео артиста
/artist/:artist/images                 список галерей/фотографий
/artist/:artist/images/:gallery        галерея
```

Почему не использовать сразу `/album/:slug` без артиста: на первом этапе каталог — один общий сайт с несколькими артистами. Артист в URL явно предотвращает конфликты одинаковых названий.

В будущем для отдельного сайта артиста можно добавить host-aware режим или другой публичный URL, не ломая внутренние сущности.

## 7. Данные и модель контента

### Текущая локальная модель

Существующая модель уже содержит полезные сущности:

- `Artist`;
- `Album`;
- `Song`;
- `Streaming`;
- изображения и галереи.

Она находится в `projects/nebuloud/src/db/`.

Недостатки текущей модели, которые исправляем постепенно:

- названия и идентификаторы местами смешаны;
- `name: string[]` у песни требует отдельного объяснения и нормализации;
- `Song.albums` допускает несколько альбомов, но это не описано явно;
- часть данных связана с представлением и файловыми путями;
- методы предметной модели находятся в классе, хотя позже Directus будет отдавать обычные объекты.

На первом шаге не переписываем все файлы вручную. Создаём frontend-модели/адаптеры поверх существующей структуры.

### Будущая модель Directus

Минимальные коллекции:

- `artists`;
- `albums`;
- `songs`;
- `videos`;
- `galleries`;
- `gallery_images`;
- возможно `streaming_links` или JSON-поле ссылок.

Связи:

- артист имеет альбомы, песни, видео и галереи;
- альбом содержит песни;
- песня может не принадлежать альбому;
- песня имеет текст;
- у сущностей есть стабильный slug/ID;
- URL не строятся по отображаемому названию напрямую.

Одинаковые названия альбомов и песен допустимы. Уникальность должна быть как минимум в пределах артиста и типа сущности.

## 8. Архитектура frontend

Предлагаемая структура одного приложения:

```text
projects/nebuloud/src/
  app/
    pages/                 страницы маршрутов
    features/              самостоятельные блоки страниц
    layout/                оболочка, header, navigation
    ui/                     простые переиспользуемые компоненты
    models/                frontend-модели
    data/                  адаптер локальных данных
    services/              content, SEO, navigation и т.п.
    app.routes.ts
    app.routes.server.ts
  db/                      текущий источник локального каталога
  styles/
    _tokens.scss
    _mixins.scss
  assets/ или public/       изображения и статические файлы
```

Переход к Directus должен выглядеть примерно так:

```text
LocalContentSource  ─┐
                     ├─ ContentService → pages/features
DirectusContentSource┘
```

Страницы не импортируют файлы конкретного артиста напрямую и не знают о формате ответа Directus.

### Контракт будущего Directus

Directus подключается после того, как локальные страницы используют нормализованные модели. На первом этапе не переносим старые TypeScript-файлы в Directus механически.

Минимальная схема:

```text
artists
  ├─ albums
  │    └─ songs
  ├─ songs
  ├─ videos
  └─ galleries
         └─ gallery_images
```

Коллекции и ключевые поля:

- `artists`: `slug`, `name`, `image`, `country`, `description`;
- `albums`: `artist`, `slug`, `title`, `year`, `cover`, `description`, `sort`;
- `songs`: `artist`, `slug`, `title`, `aliases`, `lyrics`, `authors`, `video_url`, `sort`;
- `album_songs`: `album`, `song`, `sort` — если одна песня может входить в несколько альбомов;
- `galleries`: `artist`, `slug`, `title`, `sort`;
- `gallery_images`: `gallery`, `image`, `sort`;
- `streaming_links`: `artist` или `album`, `service`, `url`, `sort`.

Правила:

- отображаемое название не является идентификатором;
- `slug` уникален в пределах артиста и типа сущности;
- песня может существовать без альбома;
- одна песня может быть связана с несколькими альбомами;
- порядок треков и фотографий хранится явно;
- Directus-ответы преобразуются в `ArtistProfile`, `CatalogAlbum` и `CatalogSong` внутри data layer;
- страницы не получают Directus SDK напрямую.

### Что переносим из `kira-sekira`

- разделение `pages / features / layout / ui`;
- Signals для состояния;
- отдельный сервис контента;
- отдельный SEO-сервис;
- SCSS design tokens;
- prerender маршрутов из списка локальных slug-ов;
- принцип: данные отдельно, представление отдельно.

### Что не переносим сейчас

- Directus snapshot и сиды;
- Docker Compose;
- Garage, backup и sync-инфраструктуру;
- отдельные приложения `main` и `models`;
- поддомены;
- собственную API-типизацию и M2M-формат Directus;
- админку.

## 9. Дизайн как первый этап

Начинаем не с базы данных и не с инфраструктуры, а с переноса визуального языка `new_design` в Angular.

### Визуальное направление

- тёмный фон;
- красно-оранжевый основной акцент;
- фиолетовые фоновые подсветки;
- полупрозрачные панели;
- тонкие границы;
- карточки с hover-состояниями;
- крупные заголовки;
- адаптивная сетка;
- навигация и breadcrumbs;
- карточки альбомов, артистов, видео и фотографий.

### Важная оговорка

`new_design` сейчас показывает много экранов, но не является единым production-дизайн-системой. Есть повторяющиеся CSS-блоки, разные варианты header/hero и демонстрационные элементы вроде эмодзи вместо изображений.

Поэтому переносим:

- композицию экранов;
- цветовое и типографическое направление;
- сетки и состояния компонентов;
- responsive-поведение.

Не переносим механически:

- inline-CSS;
- повторяющийся код из каждого HTML;
- демонстрационные emoji-placeholder;
- сомнительные анимации на каждом элементе;
- `admn.html` как обещание полноценной админки.

### Порядок визуальной реализации

1. Общие токены и базовая типографика.
2. Общий header и навигация.
3. Страница каталога артистов (`index.html`).
4. Профиль артиста (`profile.html`).
5. Карточка/список альбомов (`albums.html`).
6. Страница альбома и треклист (`album.html`).
7. Страница песни и текста (`text.html`).
8. Видео и фотографии (`video.html`, `foto.html`).
9. Адаптивная версия и состояния пустых/неполных данных.

Первый законченный срез — профиль одного артиста на реальных данных, включая переход в один альбом и одну песню. После этого расширяем на весь каталог.

- Nx;
- отдельная библиотека shared;
- Redis и сложное кеширование;
- загрузка и конвертация видео;
- платформа для массового создания сайтов;
- автоматическая миграция всего контента в Directus до проверки модели.

Это не отменённые идеи, а идеи без права мешать первому рабочему сайту.

---

## 12. Критерии готовности первого результата

Первый результат считается полезным, если:

- `npm start` запускает сайт без ручных обходов;
- каталог артистов открывается;
- профиль артиста открывается по прямой ссылке;
- из профиля можно перейти в альбом;
- из альбома можно перейти в песню;
- текст песни отображается корректно;
- страницы используют реальный каталог, а не mock-данные;
- дизайн соответствует направлению `new_design`;
- сайт работает на мобильной ширине;
- production build проходит;
- prerender не ломается на существующих маршрутах;
- добавление нового локального артиста не требует копирования Angular-компонентов.

## 13. Журнал решений

Даты здесь не фиксируем: важна актуальная договорённость, а не история изменений.

- Удалён Nx-эксперимент `feat/nx-refactor`; работа продолжается в обычном Angular `main`.
- Angular обновлён до 22.
- `pfan-stack-main_combined.txt` признан неактуальным boilerplate и не используется как основа.
- Весь существующий музыкальный каталог сохраняется.
- Directus + PostgreSQL оставлены как будущий источник контента, но не блокируют локальный frontend.
- Сначала реализуется один дизайн и рабочий вертикальный срез; темизация и multi-tenant откладываются.
- Добавлен `ContentService`: страницы больше не импортируют локальную `db` напрямую; это граница для будущего адаптера Directus.
- Локальная `db` изолирована в `LocalContentSource`; позже его можно заменить Directus-источником без изменения страниц и моделей.
- Для Nebuloud создан отдельный Docker-стек `Directus + PostgreSQL`; `kira-sekira` для этого не используется.
- Базовые коллекции, relations и идемпотентный импорт текстового каталога созданы; аватары, обложки и фотогалереи могут импортироваться в Directus Files отдельными идемпотентными скриптами.
- Добавлен прототип `DirectusContentSource`; главная страница, профиль артиста, альбом, песня, список песен и видео уже получают данные через Directus с fallback на локальный источник, фотографии пока работают через локальный источник.
- Angular-компоненты переименованы в короткий стиль без суффикса `.component`: `artist-page.ts`, `ArtistPage` и т.д.
- `ARCHITECTURE.md` — единый источник текущих архитектурных решений.
